Migration Sentinel the schema change review that runs the change before you approve it

A migration PR arrives with two statements and looks self-contained. Sentinel materialises the post-migration schema in a throwaway database, replays every statement your services issue today against it, and quotes the engine's own error text. Then it rewrites the migration as an expand/contract plan and replays that too, so phase 1 is proven backwards compatible before a human is asked to approve anything.

The reviewer's six questions

None of them are answerable from the diff. Answering all six by hand takes 20 to 40 minutes. It usually gets five.

  1. Which of the statements our services issue today touch this column?
  2. Does anything read SELECT * off the view, so the column set matters?
  3. How big is the table, and does that turn this index build into a write stall?
  4. Is there data in there right now that will not survive the change?
  5. Who deploys the code that breaks, and which lands first?
  6. Have we already had an outage from this exact pattern?

Intended user: the platform engineer on the schema review rota at a 20 to 300 engineer company. One Postgres primary, a dozen services and a BI layer reading it.

      04 / Reproduce it

      Clean machine to full comparison in under a minute

      Run the whole thing

      Python 3.11+, no pip install, no API key
      $ git clone https://github.com/MahammadRiyazShek/migration-sentinel.git $ cd migration-sentinel $ python3 eval/build_cases.py # regenerate the 12 cases $ python3 eval/run_eval.py --ablations # both baselines, pipeline, 5 ablations $ python3 -m unittest discover -s tests # 33 tests

      Expected output: results/comparison.md with 0/12 unsafe approvals for the pipeline and 1/12 for both baselines, results/ablation.md, one review packet and one trajectory per case. Wall clock on a laptop: about 0.5 s for all 12 cases and all 5 ablations. Cost: $0, because the offline model is a scripted stand-in.

      What this review did not check

      stated, never silently narrowed

      The corpus is the world. Everything the pipeline proves, it proves from the SQL it was given. Two of the twelve cases exist to expose that: case_09 hides the risky consumer in a dbt model that is not in the corpus, and case_12 hides CLUSTER invoices USING … outside the parser's model. Both are missed by construction. The mitigation is the part worth defending: an unparsed statement never becomes "safe", it travels through as an explicit unknown and lands in the packet's coverage-gap section next to everything that passed.

      Hot take

      Give an agent a tool that can be loudly wrong, and pair it with rules that can be quietly wrong. Verification is not a synonym for correctness, it is a sensor with a specific blind spot. Replay-only scored worse than rules-only on the primary metric because the most expensive hazards fail nothing at all: they lock a table or delete an invariant, and the test suite goes green.

      The corollary I did not expect: detection metrics did not move when plan generation was added, and reviewer minutes still fell by two thirds. Being right is table stakes. The tool earns its place by doing the tedious thing the human would otherwise do at 3am.
